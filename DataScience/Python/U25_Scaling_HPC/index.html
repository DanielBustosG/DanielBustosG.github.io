Sooner or later a project stops fitting in a notebook: a screening library of a million compounds, a hyperparameter sweep of five hundred fits, twenty molecular-dynamics replicas of a hundred nanoseconds each. This unit is about the engineering that follows. It begins where every optimisation should begin — with measurement, because the part of the code you think is slow usually is not — and then works outwards: vectorise, parallelise on one machine, spill to disk when the data no longer fit in memory, and finally move the whole thing to the cluster as an array job or, better, as a workflow that can be resumed after it fails at three in the morning. Two experiments in the middle deliberately make things worse, because the two commonest ways to waste a week on a cluster are parallelising with threads and parallelising too finely.

Learning objectives

  • Profile code for time and memory before optimising it, and read a profile well enough to know what to change.
  • Vectorise what can be vectorised, parallelise embarrassingly parallel loops with joblib or multiprocessing, and measure the speed-up instead of assuming it.
  • Process data larger than memory with chunking, Parquet and (where it helps) Dask.
  • Submit, monitor and organise jobs on a SLURM cluster: array jobs, dependencies, resource requests, scratch versus home, staging and checkpoint/restart.
  • Express a multi-step pipeline as a Snakemake workflow that is re-runnable, resumable and parallel by construction, and know when Nextflow is the better choice.
  • Build and use containers so that results do not depend on the machine, and decide what belongs on a laptop, a workstation, a cluster or Colab.

1. Measure first

The oldest rule in performance engineering is that programmers are bad at guessing where time goes, and the famous warning against premature optimisation is a statement about evidence, not about effort[1]. In computational chemistry the guess is wrong in a specific, repeatable way: students optimise the arithmetic and leave the parsing alone, when parsing a SMILES string into a molecule object costs more than every descriptor computed from it.

So the order of operations in this unit is fixed. Measure the workload. Find the dominant cost. Remove it if it can be removed (vectorisation, a better algorithm, a cheaper representation). Only then spend processes on it, because parallelism multiplies throughput but never makes a wasteful computation less wasteful — and on a shared cluster it multiplies the waste by the number of cores you asked for.

Domain context — the laboratory's four machines

The group computes on four kinds of machine, and most wasted time comes from running a job on the wrong one. A laptop runs analysis, figures and models on tables of up to a few hundred thousand rows; it is where this entire course runs. The laboratory workstation (many cores, a lot of memory, one consumer GPU) runs week-long jobs that must not be interrupted, local molecular-dynamics simulations — numerical integration of the equations of motion of a protein in water, producing a trajectory of coordinates over time — and model training that needs a GPU for hours. The university or national cluster (in Chile, the NLHPC) runs anything that is many independent jobs: a docking campaign over a million compounds, twenty simulation replicas, a five-hundred-point hyperparameter sweep. Colab is for teaching, for demonstrations and for a quick GPU when the workstation is busy; it is not for anything whose loss at the end of a twelve-hour session would hurt. A cluster allocation is shared, finite and audited: a job that asks for 32 cores and uses one, or a GPU job that spends its hours loading data, is charged in full and reduces the group's fair-share priority for everyone else.

The running workload for this unit is the one the laboratory actually repeats most often: compute physicochemical descriptors for every molecule in a screening library — here the frozen benchmark library of Unit 19, built from ChEMBL actives and property-matched decoys[24]. It is embarrassingly parallel — each molecule is independent of every other — which makes it the ideal case for parallelism and therefore the honest case for measuring how much parallelism really buys.

Two seconds of measurement have already decided the architecture of the project. At about a millisecond per molecule, the whole teaching library is a coffee break, a million compounds is a long lunch, and ten million is an overnight job that must be split — on one core it would occupy a laptop for the better part of a working day, and any interruption would lose all of it.

Note what the projection assumes: that the cost per molecule is constant. It is not exactly — large molecules cost more — but for planning, a linear extrapolation from a measured sample is the right instrument, and it is far better than the alternative of not estimating at all. The group's rule for cluster jobs is to measure on one per cent of the data, multiply, add fifty per cent, and request that as the time limit.

4. Vectorisation: the free speed-up, and its limit

When the computation is arithmetic over columns, the difference between writing it row by row and writing it as array expressions is not a few per cent: NumPy[21] and the libraries built on it[22] move the loop into compiled code that also uses the processor's vector instructions. The next cell scores every molecule in the library with a simple desirability function — a weighted combination of drug-likeness, lipophilicity and polar surface area — in three styles that produce identical numbers.

# The same score, three ways.
desc = library[["QED", "MolLogP", "TPSA"]].copy()

def score_rows(frame):
    '''Explicit Python loop over rows: one dictionary lookup and one float operation at a time.'''
    out = []
    for _, row in frame.iterrows():
        out.append(0.4 * row["QED"] + 0.3 * (1 - abs(row["MolLogP"] - 3) / 5)
                   + 0.3 * (1 - row["TPSA"] / 200))
    return np.asarray(out)

def score_apply(frame):
    '''pandas apply along axis 1: still one Python call per row.'''
    return frame.apply(lambda r: 0.4 * r["QED"] + 0.3 * (1 - abs(r["MolLogP"] - 3) / 5)
                       + 0.3 * (1 - r["TPSA"] / 200), axis=1).to_numpy()

def score_vectorised(frame):
    '''Array expressions: three loops in compiled C, no Python-level iteration.'''
    qed, logp, tpsa = (frame[c].to_numpy() for c in ("QED", "MolLogP", "TPSA"))
    return 0.4 * qed + 0.3 * (1 - np.abs(logp - 3) / 5) + 0.3 * (1 - tpsa / 200)

results, times = {}, {}

    t0 = time.perf_counter(); results[name] = fn(desc); times[name] = time.perf_counter() - t0
assert np.allclose(results["iterrows"], results["vectorised"])

5. Parallelism, honestly measured

An embarrassingly parallel problem is one that splits into independent pieces with no communication between them: featurising a library, docking a catalogue, running replicas of a simulation, fitting the points of a hyperparameter grid. Nearly everything the laboratory scales up is of this kind, which is fortunate, because it is the only kind that scales well without expertise.

Python offers two ways to run things at the same time, and choosing wrongly is the first failure mode of this unit. Threads share one interpreter; because of the global interpreter lock (GIL), only one thread executes Python bytecode at a time, so threads help only when the work waits on something external (network, disk) or runs inside a C library that releases the lock. Processes have separate interpreters and therefore real parallelism, at the cost of starting an interpreter per worker and of copying every argument and result through pickling.

The next cell runs the featurisation on threads.

Four threads made a CPU-bound job slower than one. Nothing is wrong with the machine: the interpreter lock means the four threads take turns executing Python, and the turn-taking itself costs time. This is the single most common wasted afternoon in the group — backend="threading" or ThreadPoolExecutor looks like parallelism and is not, unless the inner work releases the lock.

Processes do give real parallelism, and they come with their own trap, which is platform-specific. On Linux, a worker process is created by fork: the child is a copy of the parent and inherits everything already in memory, so starting a worker is cheap. On macOS (since Python 3.8) and on Windows the default is spawn: the child starts a fresh interpreter, re-imports the modules, and — crucially — re-executes the main module, which in a notebook or an unguarded script means it tries to run your whole program again. That is why multiprocessing code must live behind if __name__ == "__main__": in a script, and why starting process pools from inside a notebook kernel hangs or crashes often enough that the group's rule is simple: parallel work goes in a script.

Now the arithmetic that turns those seconds into a decision. Amdahl's law says that if a fraction $p$ of a program is parallelisable and the rest is irreducibly serial, the speed-up on $N$ workers is bounded by

$$S(N) = \frac{1}{(1-p) + p/N}.$$

Work it by hand for the plausible case $p = 0.95$ and $N = 4$: the denominator is $0.05 + 0.2375 = 0.2875$, so $S = 3.48$. With $N = 16$ the denominator is $0.05 + 0.059 = 0.109$ and $S = 9.2$; with infinitely many workers it is $1/0.05 = 20$. Five per cent of serial code caps the whole enterprise at twentyfold, no matter how large the allocation — which is why Gustafson's reply, that in practice one enlarges the problem rather than shortening the run, matters so much for science[11][12].

Running the law backwards gives the Karp–Flatt metric: from a measured speed-up $S$ on $N$ workers, the experimentally determined serial fraction is

$$e = \frac{1/S - 1/N}{1 - 1/N}.$$

The next cell computes both from the measured curve.

Three further process-parallel pitfalls complete the list, all of which the group has hit.

Oversubscription. NumPy, scikit-learn and LightGBM already use several threads internally through their linear-algebra backends. Starting eight worker processes that each start eight BLAS threads produces sixty-four threads on eight cores, and everything slows down. The fix is to set OMP_NUM_THREADS=1 (or threadpoolctl) in the workers and let the outer level own the parallelism.

Memory multiplication. Every process holds its own copy of what it receives. Four workers each receiving a two-gigabyte DataFrame need eight gigabytes, and the cluster kills the job. Pass file paths and row ranges, not data; or use joblib's memory mapping for large read-only arrays.

Unpicklable arguments. Lambdas, open file handles, database connections and RDKit molecule objects in some versions cannot be sent to a worker. Send the SMILES string and rebuild the molecule inside the worker — which is also why the worker module above takes strings.

7. The cluster: SLURM in practice

Beyond one machine, work is submitted to a scheduler, which queues jobs, allocates nodes and accounts for usage. SLURM is the one almost every academic cluster runs, including the Chilean national facility[2]. The mental model is short: you write a shell script with resource requests at the top, submit it with sbatch, and the scheduler runs it when the resources are free. Everything else is detail — but the details are where allocations are wasted.

Five of those lines deserve a sentence each, because they are the ones students get wrong.

--cpus-per-task and $SLURM_CPUS_PER_TASK. Request what you will use and read the request back in the program. Hard-coding n_jobs=32 in a job that was given 4 cores produces a job that runs slowly and annoys everyone else on the node; asking for 32 and using 1 wastes 31.

--mem and --time. Both are hard limits enforced by the kernel and the scheduler: exceeding memory kills the job immediately, exceeding the walltime kills it at the limit — usually just before the results are written. Measure on a sample, multiply, add a margin, and check afterwards with sacct what you actually used.

Scratch versus home. The home filesystem is small, backed up and shared; the scratch filesystem is large, fast, local to the cluster and periodically deleted. Jobs read and write on scratch and copy results home at the end. Running an I/O-heavy job directly on a network home directory is the most effective way to slow a cluster down for everyone.

Staging. Copy inputs in and results out explicitly. If the job dies, the trap line still removes the scratch directory; results that were never copied are lost, which is the argument for checkpointing.

Logs with %j. A log file whose name contains the job id is a log you can still read next week. A log called out.txt is overwritten by the next job.

Checkpoint and restart

A simulation that runs for three days and dies on day two with nothing written has consumed three days of allocation and produced nothing. Long jobs therefore write checkpoints: molecular-dynamics engines write a restart file every few thousand steps, a hyperparameter sweep writes each completed fit to its own file, a featurisation writes one output per shard. Three rules make checkpointing work: write to a temporary name and rename atomically (as the array script does), make every task idempotent so that resubmitting it is harmless, and record enough state to resume rather than to restart. With those in place, a job that hits its walltime can be requeued with --dependency=afternotok and finish the remainder.

8. Workflow managers: the pipeline as a graph of files

A pipeline written as a shell script runs from the beginning every time and knows nothing about what has already been done. A workflow manager inverts the description: you declare, for each output file, what inputs it needs and what command produces it, and the manager works out the rest — which steps are out of date, which can run at the same time, and how to submit them to the cluster. Re-running after a failure repeats only the missing steps, which is the property that makes a long pipeline survivable[3][4][8].

Snakemake is the one the group uses, because its rules are Python and its wildcards map naturally onto shards and replicas[3][5]. The workflow below is the course's own pipeline — curate, shard, featurise, fit, evaluate, report — written out in full.

Four features of that file carry the whole idea.

Rules are declarations, not steps. Nothing says "first curate, then featurise". Snakemake reads the input/output patterns and derives the order; asking for results/report.html pulls the entire graph.

Wildcards create jobs. features_{shard}.parquet is one rule and eight jobs, and model_{split}.joblib is one rule and two. expand() is the only place the list of shards appears.

Resources are declared per rule. threads, mem_mb and runtime travel with the rule, so the same workflow runs locally with snakemake --cores 4 and on the cluster with a profile that turns those numbers into sbatch options — no script rewriting, and no 32-core request for a job that needs two.

Environments are declared per rule. conda: envs/chem.yaml means the chemistry steps and the machine-learning steps need not share a dependency set, and the environments are rebuilt identically on another machine[9][10].

The operational commands are short: snakemake -n prints the plan without running it (always do this first), snakemake --cores 8 runs locally, snakemake --profile slurm --jobs 50 submits to the scheduler, snakemake --dag | dot -Tsvg > dag.svg draws the graph, and --report report.html produces a provenance report listing every command, version and runtime.

9. Containers: the environment as an artefact

A conda environment reproduces the Python packages. A container reproduces the operating system, the compilers, the system libraries and the Python packages, as a single immutable image with a digest. It is what makes a workflow run identically on a laptop, on a cluster node and on a reviewer's machine three years later[13][14].

Two formats matter here. Docker is the ecosystem everything is built in and requires root, which clusters do not grant. Apptainer (formerly Singularity) runs unprivileged, uses a single-file image, and mounts the user's home and scratch directories by default — which is why it is what runs on HPC[14]. The usual path is to build with Docker and convert.

Three habits make containers worth their cost[15]. Order the layers by how often they change — system packages, then dependencies, then your source — so that editing a function does not rebuild the whole image. 11. Summary

Measure, then optimise. A two-second profile showed that structure parsing and the drug-likeness score own the time in the featurisation workload, that the cheap descriptors are irrelevant, and that nothing in the hot path can be vectorised[1]. Every later decision followed from that.

Vectorise what is arithmetic. Array expressions beat row loops by two to three orders of magnitude on the same calculation, and apply is not vectorisation. But in this pipeline the vectorisable part was a rounding error next to the per-molecule C++ calls.

Parallelise what is independent, and measure the speed-up. Four processes gave clearly less than fourfold on the featurisation; Amdahl's law and the Karp–Flatt serial fraction turn that measurement into a prediction for the cluster[11][12].

Two failure modes, both exhibited. Threads made a CPU-bound job slower than a single thread, because the interpreter lock serialises Python bytecode; and dispatching microsecond tasks one at a time to four processes was two to three orders of magnitude slower than a serial loop, because the overhead per task dwarfed the task. Chunk the work, and use processes — in a script, behind a __main__ guard, because spawn re-imports the main module.

Spill to disk before you run out of memory. A streaming pass over chunks used a small fraction of the memory of a full read and gave the same answer; Parquet with column pruning is the format for working tables, Dask the tool when a table no longer fits[6].

On the cluster, think in jobs, not in machines. An array job with a concurrency limit, atomic outputs, idempotent tasks, scratch for I/O, staged inputs, logs named by job id, and a dependent merge job is the shape of nearly every campaign the group runs[2].

Let a workflow manager own the graph. Snakemake's rules, wildcards, per-rule resources and conda environments make the pipeline re-runnable, resumable and parallel by construction, and --report produces the provenance a paper needs[3][5]; Nextflow is the better choice for chains of third-party tools and multi-cloud execution[4].

Containers make the environment an artefact, pinned by digest, built with Docker, run unprivileged with Apptainer on HPC[13][14][15].

Put the job on the right machine. The cheapest optimisation available to a student is not to run the job twice.

12. Self-assessment

1. You are about to parallelise a function. What do you measure first, and why?

The serial cost per item and the profile. The cost per item decides whether the task is big enough to be worth dispatching (milliseconds, yes; microseconds, no) and lets you project the total runtime for the real data. The profile tells you whether the time is in code you could remove instead — if ninety per cent of it is in a loop that NumPy could do, vectorising is free and parallelising is not.

2. Your four-thread version is slower than the single-threaded one. Explain and fix.

The work is CPU-bound pure Python (or Python-level calls that hold the interpreter lock), so the threads take turns and add contention. The fix is processes, not threads: joblib.Parallel(backend="loky"), multiprocessing.Pool or ProcessPoolExecutor, with the work chunked so that each task is substantial. Threads remain the right answer for I/O-bound work and for libraries that release the lock internally.

3. What is the difference between fork and spawn, and why does it matter in a notebook?

Fork (the Linux default) copies the parent process, so children inherit memory and start fast. Spawn (the default on macOS and Windows) starts a fresh interpreter and re-imports the main module — in a script without an if __name__ == "__main__": guard that re-runs the whole program, and in a notebook there is no main module to re-import, so the pool hangs or crashes. The portable practice is to put parallel work in a script with the guard and run it as a process.

4. With a measured serial fraction of 0.1, what speed-up can you expect on 16 cores, and what on 64?

Amdahl gives 1/(0.1 + 0.9/16) = 6.4 on 16 cores and 1/(0.1 + 0.9/64) = 8.8 on 64. Quadrupling the cores bought 37 % more speed. The practical conclusion is to request 16, not 64: the extra cores spend longer in the queue, are charged in full, and deliver almost nothing.

5. A colleague's array job asks for 32 cores per task and uses one. What are the three consequences?

The job waits far longer in the queue, because 32 free cores are rarer than one; the allocation is charged for 32 cores times the walltime, so the group's budget drains 32 times faster; and the fair-share priority of everyone in the group falls, so the next job queues longer too. sacct --format=JobID,Elapsed,AllocCPUS,MaxRSS after the fact is how the mismatch is discovered.

6. Why does the array script write to $OUT.tmp and then rename?

Because a rename within a filesystem is atomic: the output file either does not exist or is complete. If the task is killed halfway — walltime, memory, node failure — the partial file is a .tmp that nobody mistakes for a result, and the if [[ -f "$OUT" ]] guard at the top makes resubmitting the task harmless. Together they make the array idempotent, which is what allows --array=7,23,88 to repair a campaign.

7. What does a workflow manager give you that a shell script does not?

A dependency graph derived from file names, which yields three things a script cannot: re-running only what is out of date (resumability after a crash), automatic parallelism over independent jobs, and a provenance record of which command produced which file with which versions. It also separates resource declarations from the submission mechanism, so the same workflow runs on a laptop and on SLURM.

8. In the Snakemake workflow, which jobs run at the same time, and what limits them?

The eight featurisation jobs, because their inputs are independent shards and none is an input to another; and, later, the two fitting jobs, one per split. The limit is the budget given on the command line — --cores locally, --jobs for submitted jobs — intersected with the threads each rule declares. Nothing in the file changes between the two situations.

9. Why build a container with Docker but run it with Apptainer on the cluster?

Docker is where the tooling, base images and registries live, but its daemon requires root, which no cluster grants to users. Apptainer runs unprivileged, stores the image as a single file the user owns, and mounts home and scratch by default, so it fits the HPC security model. Converting a Docker image to a .sif is one command, so the ecosystem and the execution model can be chosen independently.

10. Estimate the cost of forgetting to fix a random seed in a 12-hour GPU experiment that must therefore be repeated.

Twelve GPU-hours: roughly 4-5 kWh once the data-centre overhead is included, of the order of two kilograms of CO2e on a grid at 400 g/kWh, and tens of dollars at on-demand cloud prices — plus twelve hours of queue and of your own time. The arithmetic is in Section 10, and the preventive measure costs one line of code.

11. When is Dask the right answer, and when is it a complication?

It is right when a single table genuinely exceeds memory, when the data are already partitioned across many files, or when the same computation must later run on a cluster of machines. It is a complication when a chunked pandas loop or a Parquet file with column pruning would do, because lazy evaluation makes debugging harder and the scheduler adds overhead that only pays off at scale. Measure the chunked version first.

12. Size two campaigns over the same million compounds: featurising them, and docking them. Which belongs on the cluster?

Featurisation first, with the rate measured in Section 1 (about 1.2 ms per molecule): 106 x 1.2 ms is roughly 1,200 s, that is about 20 minutes of serial work, or 0.3 core-hours. Four worker processes on a laptop finish it in about five minutes, so it does not belong on the cluster at all — the queue wait alone would exceed the job.

Docking the same library is a different problem: at an optimistic 30 s per molecule it is 3 x 107 s, about 8,300 core-hours, which no single machine will do. Shard the shuffled library into 1,000 pieces of 1,000 compounds; each piece is about 8.3 core-hours, so with --cpus-per-task=4 a task runs for roughly 2 h. Submit --array=0-999%50 --cpus-per-task=4 --mem=8G --time=04:00:00: fifty concurrent slots means twenty waves of about 2 h each, roughly two days of wall-clock time. Write each shard atomically to scratch and copy results home, add a merge job with --dependency=afterok, and run one shard interactively before submitting the array. The lesson is the comparison: the decision to use a cluster follows from the measured cost per item, not from the number of items.

Glossary

Amdahl's law
The bound S(N) = 1/((1-p) + p/N) on the speed-up achievable with N workers when a fraction p of the work is parallelisable.
Apptainer (Singularity)
Container runtime designed for HPC: unprivileged execution, single-file images, user directories mounted by default.
Array job
One SLURM submission that runs the same script many times with a different task index, optionally with a concurrency limit.
Checkpoint/restart
Writing enough intermediate state that a killed job resumes rather than restarts; atomic renames and idempotent tasks make it safe.
Chunking
Processing a file in pieces (pandas.read_csv(chunksize=...)) so that peak memory is set by the chunk, not by the file.
Embarrassingly parallel
A workload that splits into independent tasks with no communication; the only kind that scales well without expertise.
fork / spawn
The two ways a worker process is created: a copy of the parent (fast, Linux default) or a fresh interpreter that re-imports the main module (macOS and Windows default).
Global interpreter lock (GIL)
The CPython mechanism allowing only one thread to execute Python bytecode at a time; the reason threads do not speed up CPU-bound Python.
Karp-Flatt metric
The serial fraction e = (1/S - 1/N)/(1 - 1/N) inferred from a measured speed-up; its growth with N indicates overhead rather than serial code.
Oversubscription
Starting more threads or processes than there are cores, typically by combining an outer process pool with multi-threaded numerical libraries.
Parquet
A compressed columnar file format that supports reading a subset of columns and partitioning across directories.
Profiling
Measuring where a program spends time (cProfile, timeit) or memory (tracemalloc) before changing it.
Scratch filesystem
Fast, large, temporary cluster storage for job input and output, as opposed to the small, backed-up home filesystem.
SLURM
The scheduler most academic clusters run: sbatch to submit, squeue to monitor, sacct to audit what a finished job used.
Snakemake rule / wildcard
A declaration of how to produce output files from input files, and the pattern variable that turns one rule into many jobs.
Workflow manager
A tool that derives execution order from file dependencies, re-runs only what is out of date and submits jobs to a scheduler.
