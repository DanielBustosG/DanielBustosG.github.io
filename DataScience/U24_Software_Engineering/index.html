A notebook is an excellent laboratory bench and a poor product. The code in it runs once, in one order, on one machine, with results that live in the output cells rather than in files. This unit performs the conversion that every long-lived piece of laboratory software goes through: the curation protocol of Unit 6 becomes an installable package with modules, a configuration file, a command-line interface, a test suite, a linting configuration, continuous integration, a licence and a citation file. The package is written into a temporary directory by the notebook itself, imported, exercised, tested, broken on purpose, repaired and finally deleted — so that everything claimed here is demonstrated rather than described.

Learning objectives

  • Refactor notebook code into a package (src layout, modules, functions with docstrings, a CLI with argparse) without changing the results — and prove it with tests.
  • Write unit and regression tests with pytest (fixtures, parametrisation, tolerances for floats, golden files, property-style invariants), measure coverage, and run the suite automatically with GitHub Actions.
  • Use logging, configuration files, type hints, linters and formatters (ruff, black) and semantic versioning.
  • Document a package in its four layers — README, docstrings, tutorial, API reference — and make it citable with a CHANGELOG, a licence and a CITATION.cff.
  • Review someone else's code constructively, and receive a review without taking it personally.

1. Why the notebook has to end

Every thesis in the laboratory starts the same way: a notebook that loads a table, cleans it, computes something and draws a figure. That is the correct way to start — the notebook is the default working instrument of data science for good reasons[15]. The trouble appears six months later, when a second student needs the same cleaning for a different target, when a referee asks what exactly was excluded, or when the first student graduates and the notebook is the only description of a protocol that three papers depend on.

Notebooks fail as software for four specific reasons, all of them measurable. Their execution order is not the order of the cells, so a notebook that runs correctly for its author may not run at all from top to bottom — a large-scale study of public notebooks found that only a small minority reproduced their own stored outputs[16]. Their state is invisible: a variable defined in a deleted cell survives in memory and silently supports the rest of the analysis. They have no interface, so the only way to reuse the logic is to copy it, and copies diverge. And they cannot be tested, because there is nothing addressable to test.

The remedy is not to abandon notebooks — they remain the right medium for exploration, for teaching and for the narrative that accompanies a result[17]. The remedy is to move the parts that other people depend on into a package, and to let the notebook import it. The notebook then keeps the story and loses the responsibility. This is the organising idea behind every published set of rules for reproducible computational research[9][4], and it is the practice that the reproducibility surveys of the last decade found missing[18][10].

Domain context — what the group's code is actually for

Three pipelines in the laboratory outlive any single student: the curation of bioactivity data downloaded from ChEMBL into a modelling-ready table (the subject of this unit), the post-processing of virtual-screening campaigns into ranked lists with early-recognition metrics, and the analysis of molecular-dynamics trajectories into observables and their uncertainties. Each is used by several projects at once, and each produces numbers that end up in publications. When a paper carries a software-availability statement — "the code is available at …" — it commits the group to something concrete: the repository must exist, it must contain what produced the numbers, it must run on a machine that is not yours, and it must say what it does. Research software that cannot be rerun is a liability for the laboratory, not an asset[1][3], and software errors have retracted real papers[24][25], invalidated the statistics of a whole imaging literature[26] and corrupted thousands of gene lists through a spreadsheet default[27]. The data these pipelines consume come from public databases with their own release cycles[31], and they are processed with libraries that are themselves research software to be pinned and cited[29][30].

There is a second, newer reason to care. A large share of the code written in the group now begins as a suggestion from a language model. Such code is usually syntactically fine, frequently subtly wrong, and always written without knowledge of your data. Tests are what make it safe to accept: a suggestion that passes a regression test against a known-good output is a contribution, and one that does not is a bug caught in seconds rather than in review.

That cell works. It is also unusable as software, and the reasons are worth naming one by one, because the refactoring in the next section is simply the removal of each.

  1. It mixes input, computation and output: the file is read, the chemistry is computed and the table is produced in one block, so none of the three can be exercised without the others.
  2. It communicates through notebook state: d is reassigned nine times, and the meaning of d depends on how many cells above it have run.
  3. Its parameters are buried: the heavy-atom window 3, 70, the concentration bounds and the unit table are literals in the middle of expressions, invisible to anyone reading the Methods.
  4. It has no interface: another project wanting the same protocol must copy the cell, and the copy will not receive the fix made next month.
  5. It cannot report what it did: the exclusion counts exist only as the difference between two len() calls that nobody printed.

2. Refactoring: pure functions with the input and output at the edges

The pattern that fixes all five is older than data science. Write pure functions — a function whose output depends only on its arguments and which changes nothing outside itself — for the computation, and keep reading and writing at the edges of the program[1][2]. A pure function is testable by construction: call it with an input, compare with the expected output, no fixtures, no files, no order dependence.

Applied to the curation protocol, the decomposition is almost forced by the data flow: a function that standardises one structure, a function that applies one filter and reports how many rows it removed, a function that aggregates measurements into compounds, and a thin orchestrator that runs them in order and returns the table plus the log. Reading and writing live in a separate module that the computation never imports.

# The same protocol as pure functions, defined here before they move into the package.
from dataclasses import dataclass

@dataclass(frozen=True)
class Standardised:
    '''Result of standardising one structure; frozen so it cannot be modified by mistake.'''
    smiles: str | None
    inchikey: str | None
    heavy_atoms: float

def standardise_smiles(smiles, normalizer=None, uncharger=None, chooser=None):
    '''Canonical parent SMILES, InChIKey and heavy-atom count, or a null record if unparsable.'''
    normalizer = normalizer or rdMolStandardize.Normalizer()
    uncharger = uncharger or rdMolStandardize.Uncharger()
    chooser = chooser or rdMolStandardize.LargestFragmentChooser()
    mol = Chem.MolFromSmiles(smiles) if isinstance(smiles, str) else None
    if mol is None:
        return Standardised(None, None, float("nan"))
    try:
        mol = uncharger.uncharge(chooser.choose(normalizer.normalize(mol)))
        Chem.SanitizeMol(mol)
    except Exception:
        return Standardised(None, None, float("nan"))
    return Standardised(Chem.MolToSmiles(mol), Chem.MolToInchiKey(mol),
                        float(mol.GetNumHeavyAtoms()))

def aggregate_measurements(frame):
    '''One row per InChIKey: median of the exact values, or of the censored ones if none is exact.'''
    out = []
    for key, g in frame.groupby("inchikey", sort=True):
        exact = g.loc[~g["censored"]]
        use = exact if len(exact) else g
        out.append({"inchikey": key, "pActivity": float(use["pActivity"].median()),
                    "censored": bool(len(exact) == 0), "n_measurements": int(len(g)),
                    "n_exact": int(len(exact))})
    return pd.DataFrame(out)

3. The package on disk

A Python package is a directory of modules plus a pyproject.toml that tells the packaging tools how to build and install it. The layout used by the group is the src layout: the importable code lives under src/<package>/ rather than at the repository root. The reason is mechanical and important — with a src layout, import rockcurate can only succeed if the package was installed (or its src directory was put on the path deliberately), so the tests cannot accidentally pass by importing the working copy while the installed one is broken.

The package below is written to a temporary directory by the notebook. Nothing is installed; the directory is added to sys.path, which is the same thing an editable install does, done by hand so that the mechanism is visible.

    def record(self, code: str, description: str, n_before: int, n_after: int) -> None:
        <<DQ>>Append one step to the log.<<DQ>>
        self.steps.append({"code": code, "description": description,
                           "n_removed": n_before - n_after, "n_rows": n_after})
        logger.info("%s: removed %d rows, %d remain", code, n_before - n_after, n_after)

    def frame(self) -> pd.DataFrame:
        <<DQ>>Return the log as a DataFrame, suitable for a supplementary table.<<DQ>>
        return pd.DataFrame(self.steps)


def apply_filters(frame: pd.DataFrame, cfg: Config, log: CurationLog) -> pd.DataFrame:
    <<DQ>>Apply the row filters of the protocol in order, logging each exclusion.<<DQ>>
    steps = [
        ("E01", "no deposited structure", lambda f: f["canonical_smiles"].notna()),
        ("E02", "target organism is not the configured one",
         lambda f: f["target_organism"].eq(cfg.organism)),
        ("E03", "ChEMBL data_validity_comment flag",
         lambda f: f["data_validity_comment"].isna() if cfg.drop_validity_flagged
         else pd.Series(True, index=f.index)),
        ("E04", "no numeric standard_value", lambda f: f["standard_value"].notna()),
    ]
    for code, description, predicate in steps:
        before = len(frame)
        frame = frame.loc[predicate(frame).to_numpy()]
        log.record(code, description, before, len(frame))
    return frame


def harmonise_units(frame: pd.DataFrame, cfg: Config, log: CurationLog) -> pd.DataFrame:
    <<DQ>>Add ``value_nM`` and drop rows whose unit is unknown or whose value is implausible.<<DQ>>
    nanomolar = frame["standard_units"].map(UNITS_TO_NM) * frame["standard_value"]
    frame = frame.assign(value_nM=nanomolar)
    before = len(frame)
    frame = frame.loc[frame["value_nM"].notna().to_numpy()]
    log.record("E05", "unit not convertible to nM", before, len(frame))
    before = len(frame)
    frame = frame.loc[frame["value_nM"].between(cfg.min_value_nm, cfg.max_value_nm).to_numpy()]
    log.record("E06", "implausible concentration", before, len(frame))
    return frame


def add_structures(frame: pd.DataFrame, cfg: Config, log: CurationLog) -> pd.DataFrame:
    <<DQ>>Standardise every unique structure once and keep rows inside the heavy-atom window.<<DQ>>
    records = {s: standardise_smiles(s) for s in frame["canonical_smiles"].unique()}
    frame = frame.assign(
        std_smiles=[records[s].smiles for s in frame["canonical_smiles"]],
        inchikey=[records[s].inchikey for s in frame["canonical_smiles"]],
        heavy_atoms=[records[s].heavy_atoms for s in frame["canonical_smiles"]],
    )
    before = len(frame)
    frame = frame.loc[frame["inchikey"].notna().to_numpy()]
    log.record("E07", "structure could not be standardised", before, len(frame))
    before = len(frame)
    inside = frame["heavy_atoms"].between(cfg.min_heavy_atoms, cfg.max_heavy_atoms)
    frame = frame.loc[inside.to_numpy()]
    log.record("E08", "outside the small-organic window", before, len(frame))
    return frame


def derive_activity(frame: pd.DataFrame) -> pd.DataFrame:
    <<DQ>>Add ``pActivity`` (-log10 of the molar value) and the censoring flag.<<DQ>>
    return frame.assign(
        pActivity=9.0 - np.log10(frame["value_nM"]),
        censored=~frame["standard_relation"].fillna("=").eq("="),
    )


def aggregate_measurements(frame: pd.DataFrame) -> pd.DataFrame:
    <<DQ>>Collapse measurements to one row per InChIKey.

    The median of the exact measurements is used when a compound has any; compounds
    whose measurements are all censored keep the median of the censored values and are
    flagged. Returns a frame sorted by InChIKey, so the output is deterministic.
    <<DQ>>
    rows = []
    for key, group in frame.groupby("inchikey", sort=True):
        exact = group.loc[~group["censored"]]
        used = exact if len(exact) else group
        rows.append({
            "inchikey": key,
            "std_smiles": group["std_smiles"].iloc[0],
            "pActivity": float(used["pActivity"].median()),
            "censored": bool(len(exact) == 0),
            "n_measurements": int(len(group)),
            "n_exact": int(len(exact)),
        })
    return pd.DataFrame(rows)


def curate(frame: pd.DataFrame, cfg: Config | None = None) -> tuple[pd.DataFrame, CurationLog]:
    <<DQ>>Run the whole protocol on a raw ChEMBL activity table.

    Parameters
    ----------
    frame : pandas.DataFrame
        Raw activity records as delivered by the ChEMBL API.
    cfg : Config, optional
        Protocol parameters; the defaults reproduce the laboratory's reference table.

    Returns
    -------
    (pandas.DataFrame, CurationLog)
        One row per standardised compound, and the per-step exclusion log.
    <<DQ>>
    cfg = cfg or Config()
    log = CurationLog()
    log.record("E00", "raw records as delivered", len(frame), len(frame))
    frame = apply_filters(frame, cfg, log)
    frame = harmonise_units(frame, cfg, log)
    frame = add_structures(frame, cfg, log)
    frame = derive_activity(frame)
    table = aggregate_measurements(frame)
    log.record("A09", "aggregated to one row per compound", len(frame), len(table))
    return table, log
'''

6. Tests: what to assert, and how

A test suite for scientific code has four layers, and most student projects write only the first.

Unit tests check one function against a hand-computed answer. They are fast, they localise failures precisely, and they are the only tests whose expected values you can reason about completely — like the aggregation worked by hand in Section 2.

Parametrised tests run the same assertion over a table of cases. In chemistry this is how edge cases are documented: a salt, a charged species, an unparsable string, a molecule with an unusual valence. Each row of the table is a case somebody once got wrong.

Property tests assert an invariant that must hold for every input rather than a specific output. The protocol has two: standardising an already-standardised structure must change nothing (idempotence), and aggregating a table that already has one row per compound must return it unchanged. Invariants catch classes of bug that example-based tests miss, because they do not depend on your having imagined the failing input[21].

Regression (golden-file) tests compare the output of the whole pipeline with a stored, reviewed result — here the reference table of 4,280 compounds. They are the tests that make refactoring safe, and the only ones that would have caught the protocol change recorded in the changelog's 0.3.0 entry. Scientific software is unusually dependent on them, because for most of its functions nobody knows the right answer in advance: the literature on testing computational science calls this the oracle problem, and a reviewed stored output is the practical oracle[28].

Two mechanical points. Floating-point results are compared with a tolerance (pytest.approx, numpy.testing.assert_allclose), never with ==; the tolerance is a scientific decision and should be justified in a comment. And randomness is tested by fixing the seed and asserting reproducibility, not by asserting a particular random value.

7. Coverage: useful, and not a goal

Coverage measures which lines of the package were executed while the tests ran. It answers one question — is there code nobody tested? — and it answers no other. A suite can reach full coverage while asserting nothing, and a well-tested numerical routine can sit at seventy per cent because its error branches are hard to trigger. The group's rule is to look at the uncovered lines and decide, one by one, whether each is a missing test or an acceptable gap.

8. The bug that passes the unit tests

The changelog of the package records a real protocol change at version 0.3.0: aggregation used to take the median of all measurements of a compound and was changed to take the median of the exact ones only. Suppose a well-meaning refactoring reverted it — a single line, used = exact if len(exact) else group becoming used = group. The code still runs, the output still has the right shape, and most of the test suite still passes.

Three lessons follow, and they are the reason the group insists on regression tests for pipelines.

First, a bug that changes a scientific result need not break anything. The buggy pipeline produces a table of exactly the right size with plausible values, and touches only the one per cent of compounds that have both exact and censored measurements — which is precisely why nobody would notice. Without a stored reference, the only way to catch it would be for somebody to re-derive a number by hand.

Second, test layers are not interchangeable. The property tests are valuable and they could not have caught this, because idempotence holds for the buggy rule too. A suite with only property tests, or only unit tests of helper functions, has a hole exactly where the science lives.

Third, the golden file must be reviewed, not merely stored. A regression test pins the output to whatever was there when it was written; if the stored table had itself been produced by the buggy code, the test would now enforce the bug. The reference table of this course was checked against a published protocol and a hand-worked example before being frozen, and that check is what gives the test its authority.

9. Linting, formatting and pre-commit

Style is not an aesthetic question in a shared repository; it is a question of how much of a review is spent on things a machine could have said. The group uses ruff, which replaces flake8, isort, pydocstyle and several plugins with one fast tool configured in pyproject.toml, and ruff format (a black-compatible formatter) to remove formatting from the conversation entirely. The rules selected in the package's configuration — E, F, I, UP, B, D — cover style errors, likely bugs, import order, outdated idioms, common pitfalls and missing docstrings.

11. Versions, changelogs and citation

A package that other work depends on needs a version number that means something. Semantic versioning encodes compatibility in three integers: MAJOR.MINOR.PATCH, where a patch fixes a bug without changing behaviour, a minor release adds functionality compatibly, and a major release breaks something. The licence decision is equally mechanical. Taken together, a versioned repository with a licence, a citation file, a changelog and an archived release is what the FAIR principles for research software ask for[7], and it is also the minimum that makes a project open to contributions from outside the group rather than readable only[8].

13. Reviewing code, and being reviewed

Code review in a laboratory is not quality control by a superior; it is two people making sure that a piece of work can be defended. Industrial studies of review practice find that its measured value lies less in defect detection than in knowledge transfer and in the readability of what survives[22][23] — which is precisely what a research group needs when a student leaves.

The etiquette matters as much as the checklist. Review the code, not the author: "this function reads the file twice" rather than "you did not think about efficiency". Distinguish a blocking objection from a preference, and say which it is — the convention is to prefix non-blocking remarks with "nit:". Ask questions when you do not understand instead of assuming an error. Approve when the change is an improvement, not when it is perfect; a review that demands perfection stops work. And on the receiving side: a review comment is information about your code, not about you, and the correct response to a good catch is to say so and fix it.

14. Summary

A notebook is a bench, a package is an instrument. The conversion is mechanical: pure functions for the computation, I/O at the edges, parameters in a configuration object, a thin command-line interface, and a pyproject.toml that makes the whole thing installable[1][2].

Refactoring is only safe with a reference. The functions extracted in Section 2 reproduced the laboratory's curated table to within the precision of the stored file, and that comparison became the regression test that guards every later change.

Four layers of tests, each catching what the others cannot. Unit tests against hand-computed answers, parametrised tests over edge cases, property tests for invariants such as idempotence, and golden-file regression tests for the pipeline as a whole[21]. The injected one-line bug of Section 8 passed the structure, property and command-line tests and was caught only by the hand-worked unit test and the golden file — after changing the reported potency of 39 compounds by a median of half a log unit and up to 1.5.

Coverage is a diagnostic, not a target. Read the uncovered lines; a suite can reach any percentage while asserting nothing.

Automate the arguments away. ruff and pre-commit remove style from review; a four-job CI matrix removes "works on my machine"; a coverage gate removes the slow erosion of the suite.

Make the software citable and the changes legible. Semantic versioning with a research-specific rule — anything that changes published numbers is a breaking change — a CHANGELOG that says what changed, a licence, and a CITATION.cff[5][6].

Review is knowledge transfer. The checklist finds defects; the conversation is what keeps a pipeline usable after its author has graduated[22].

15. Self-assessment

1. Why does the group use a src layout instead of keeping the package at the repository root?

Because with the code under src/ an import rockcurate cannot be satisfied by the working directory. The tests therefore exercise the installed package — the thing a user receives — rather than the files you happen to be editing, and a packaging mistake (a module missing from the distribution, a missing dependency) fails the test run instead of hiding until someone else installs it.

2. What makes a function "pure", and why does purity make testing cheap?

Its result depends only on its arguments, and it changes nothing outside itself: no global state, no file reads, no logging of results into module variables. Such a function is tested by calling it and comparing the return value — no fixtures, no temporary files, no ordering between tests. In this package aggregate_measurements is pure and is tested against a five-row hand-built frame; read_raw is not pure and is tested with a tmp_path fixture.

3. Give the hand-worked aggregation example and the number the buggy version would produce.

Compound A has measurements 7.0 and 7.4 (exact) and 6.2 (censored). The protocol takes the median of the exact values, 7.20. The reverted rule takes the median of all three, 7.0. The difference is 0.2 log units for that compound, and across the real data set the bug changed the potency of 39 compounds — about one per cent — by a median of half a log unit and by as much as 1.5, three times the experimental error, moving three compounds across the potency threshold used for classification.

4. A colleague says their test suite has 100 % coverage, so the code is correct. Respond.

Coverage measures which lines ran, not whether anything was checked. A suite that calls every function and asserts nothing reaches 100 %. Conversely, the uncovered lines in this package are defensive branches whose absence from the suite is a deliberate, documented decision. Coverage is useful read line by line — as a list of untested code — and misleading as a single number to maximise.

5. Which kind of test would have caught a change in the unit-conversion table, and which would not?

A parametrised unit test asserting that 1 nM gives pActivity 9 and 1,000 nM gives 6 catches it immediately. The golden-file test catches it too, but only reports that the whole pipeline moved. Property tests do not: idempotence and determinism hold for the wrong conversion as well. This is why the suite has layers — the unit test localises, the golden test guarantees.

6. Why did the buggy package have to be tested in a subprocess?

Because rockcurate was already imported into the notebook's interpreter, and Python caches modules in sys.modules: editing the file on disk does not change the imported module, and deleting it from the cache would leave stale references in objects already created. A separate process with PYTHONPATH pointing at the patched copy gives an unambiguous answer. The same reasoning applies to any "I fixed it" claim made without restarting the kernel.

7. What belongs in a configuration file, and what belongs in the code?

Values a user may legitimately change for their project — the organism, the heavy-atom window, the plausibility bounds — belong in configuration, with defaults in the code that reproduce the published protocol. The structure of the protocol itself, the order of the filters and the aggregation rule do not: making them configurable would turn a reproducible protocol into a family of protocols with no name. The test test_defaults_are_the_published_protocol is what prevents the defaults from drifting.

8. Under the group's versioning rule, what version number follows 1.4.2 after a fix that changes the output of the curation by 0.05 log units?

2.0.0. The interface did not change, so semantic versioning in its usual reading would suggest 1.4.3, but any change that alters published numbers is treated as breaking: papers citing 1.4.2 and 2.0.0 report different results from the same input, and a reader must be able to see that from the version alone. The CHANGELOG entry must say which numbers moved and by how much.

9. What does a "software availability" statement commit the group to?

That a repository exists at the stated address, that it contains the code that produced the published numbers (tagged or archived at a DOI, not just the current main branch), that it declares its dependencies and licence, and that it runs somewhere other than the author's laptop — which is what continuous integration demonstrates. Anything less turns the statement into a claim the group cannot support.

10. Write three review comments on a pull request that adds a new filter to the protocol, in the group's style.

"Blocking: this filter changes the compound count, so the golden test needs updating and the CHANGELOG needs a breaking-change entry — can you add both?"; "Could you move the 0.35 similarity cut-off into Config? It is the kind of number a reviewer will ask about and it should have one definition."; "nit: f is hard to search for; filter_by_similarity would be easier to find in six months." The first is blocking and scientific, the second structural, the third a preference marked as such.

11. Your package produces a figure as a side effect inside a computation function. Why is that a design error, and what is the fix?

Because it mixes a pure computation with an output action: the function cannot be called in a loop, on a cluster or inside a test without producing files or opening windows, and its result can no longer be compared to an expected value. The fix is to return the numbers and let a separate plotting function — or the notebook — draw them. The same argument applies to functions that print.

12. A language model wrote a plausible implementation of a new aggregation rule. What do you do before merging it?

Read it, then make it earn its place in the suite: add a hand-worked unit test for the new rule, check that the existing golden test either still passes or fails for a reason you can explain, run ruff, and record the behavioural change in the CHANGELOG with a version bump. The tests are the contract; whether a human or a model wrote the code changes nothing about what must be demonstrated before it is trusted.

Glossary

Continuous integration (CI)
Automatic execution of the test suite on a clean machine on every push, across a matrix of operating systems and language versions.
Coverage
The fraction of statements executed while the tests run; a diagnostic listing untested code, not a quality score.
Fixture
A pytest-managed object (a temporary directory, a small DataFrame, a loaded reference table) that tests request by naming it as an argument.
Golden-file (regression) test
A test comparing the output of a pipeline with a stored, reviewed reference; the guard that makes refactoring safe.
Idempotence
The property that applying an operation twice gives the same result as applying it once; here, standardising an already standardised structure.
Linter / formatter
Tools that report likely defects and style violations (ruff) and rewrite code into a canonical form (ruff format, black).
Parametrised test
One test function run over a table of input/expected pairs, each reported separately by name.
Pre-commit hook
A check that runs automatically before a commit is created, keeping failing code out of the history.
Property test
A test asserting an invariant that must hold for every input, rather than a specific output for a specific input.
Pure function
A function whose result depends only on its arguments and which changes nothing outside itself.
pyproject.toml
The single declarative file describing how a Python project is built, what it depends on, what scripts it installs and how its tools are configured.
Semantic versioning
MAJOR.MINOR.PATCH numbering encoding compatibility; in this group extended so that any change to published numbers is a major release.
src layout
Repository structure placing importable code under src/, so that tests exercise the installed package rather than the working copy.
Type hint
An annotation declaring the expected types of arguments and return values; documentation that a checker can verify.
