A molecule lives in a computer only as text or as a file. Before you can search a million compounds, train a model or deduplicate a vendor catalogue, you must agree on how a structure is written down — and, just as importantly, on a canonical way to write it so that two people who drew the same molecule produce the same string. This unit is about that representation layer: the SMILES line notation and its grammar, the InChI and InChIKey identifiers, the MOL/SDF and PDB file formats, and the round-trips between them that are where most real-world data bugs are born. For a computer scientist the theme is familiar — serialisation, canonical forms, hashing, lossy versus lossless encodings — applied to the labelled graph that Unit 1 said a molecule is.

1. From a drawing to a string: why molecules need notations

A chemist on paper draws a molecule: lines for bonds, letters for the heteroatoms, carbons and hydrogens left implicit. A drawing is unambiguous to a human but useless to a program that must store, sort, search and compare millions of structures. We need a machine-readable representation: a way to serialise the molecular graph of Unit 1 into something a computer can store in a column, index in a database and compare for equality.

Three kinds of representation dominate cheminformatics, and this unit covers all three. A line notation writes the whole molecule as a single string — compact, human-typable, database-friendly; SMILES is the universal one.[1] A registry identifier is a canonical string designed so that the same molecule always yields the same identifier, for exact-match lookup and deduplication; the InChI and its hashed form the InChIKey are the open standard.[3] A connection-table file format stores the graph as explicit atom and bond tables, optionally with 2-D or 3-D coordinates and arbitrary data fields; MOL/SDF[6] and, for 3-D structures, PDB[7] are the workhorses. (A fourth kind, a chemical name such as "acetylsalicylic acid", is also machine-parseable — tools such as OPSIN convert names to structures[16] — but names are verbose and ambiguous and we will not use them as a data format.) The choice among the three is the recurring design decision of the whole field,[19] and getting it wrong is the commonest source of silent error in a cheminformatics pipeline.[24]

Chemistry box — a drawing, an identifier and a file are not the same thing

A drawing (or a SMILES you typed) communicates a structure but may be written many different ways. An identifier (InChIKey) is a canonical label designed for one purpose: deciding whether two records are the same molecule. A file format (MOL/SDF/PDB) is a container that can also carry coordinates and data. For a computer scientist: a SMILES is like source code (many spellings compile to the same program), a canonical SMILES or InChI is like a normalised/canonical form, and an InChIKey is like a content hash used as a primary key.

The cell below makes the three representations concrete on one molecule — aspirin — so you can see them side by side before we take each apart.

# One molecule, three representations: a SMILES string, an InChI, and an InChIKey hash.
smi = "CC(=O)Oc1ccccc1C(=O)O"                      # aspirin, as typed by a human
m = Chem.MolFromSmiles(smi)
print("input SMILES   :", smi)
print("canonical SMILES:", Chem.MolToSmiles(m))    # RDKit's canonical spelling
print("molecular formula:", rdMolDescriptors.CalcMolFormula(m))
print("InChI          :", MolToInchi(m))
print("InChIKey       :", MolToInchiKey(m))         # a fixed-length hash: the 'primary key'
Draw.MolToImage(m, size=(320, 220))

Figure 1. Aspirin in three representations and as a drawing. The input SMILES is one of many legal spellings; RDKit's canonical SMILES is the one preferred spelling it computes. The InChI is a layered string built by a fixed algorithm (note the slash-separated layers: formula C9H8O4, then connectivity c, hydrogens h, …). The InChIKey is a 27-character hash of that InChI — the 14 letters before the first hyphen encode the connectivity skeleton, the next block encodes stereochemistry and other layers. The four lines are increasingly "canonical": the input SMILES varies by who typed it, the InChIKey is the same for anyone who draws this molecule. We now unpack each, starting with SMILES.

2. The SMILES grammar, piece by piece

SMILES — Simplified Molecular Input Line Entry System — was introduced by David Weininger in 1988[1] and is still the most widely used molecular string. It is a depth-first serialisation of the molecular graph: you walk the atoms, writing each as you visit it, using parentheses for branches and digits to mark the bonds that close rings. The full grammar is specified in the Daylight theory manual;[26] we build it up in five pieces — atoms, bonds, branches, ring closures, and the decorations (charge, isotope, stereo) — each with code that shows the piece on real molecules.

2.1 Atoms

Atoms are written by their element symbol. The ten elements of the organic subset — B, C, N, O, P, S, F, Cl, Br, I — are written bare (C, N, O, Cl, …) and their hydrogens are filled in automatically to satisfy the normal valence of Unit 1 (C wants 4 bonds, N 3, O 2). Any other atom, or any atom that needs an explicit charge, isotope or hydrogen count, is written in square brackets with everything spelled out: [nH] is an aromatic nitrogen bearing one hydrogen, [Na+] a sodium cation, [13C] a carbon-13. Lowercase letters mean the atom is aromatic (part of a delocalised ring, Unit 1): c is aromatic carbon, n aromatic nitrogen. The cell shows how RDKit fills in the implicit hydrogens that the bare organic-subset atoms imply.

# Organic-subset atoms get implicit hydrogens to satisfy valence; bracket atoms spell everything out.
rows = []
for label, smi in [("methane C", "C"), ("ammonia N", "N"), ("water O", "O"),
                   ("methanol CO", "CO"), ("chloromethane CCl", "CCl"),
                   ("methane [C] bracketed", "[C]"), ("ammonium [NH4+]", "[NH4+]")]:
    m = Chem.MolFromSmiles(smi)
    a0 = m.GetAtomWithIdx(0)
    rows.append((label, smi, a0.GetSymbol(), a0.GetTotalNumHs(), a0.GetFormalCharge()))
print(pd.DataFrame(rows, columns=["molecule", "SMILES", "atom0", "implicit+explicit H on atom0", "charge"]).to_string(index=False))

The table shows the rule in action: a bare C becomes methane (CH4, four implicit hydrogens), a bare N ammonia (three), a bare O water (two) — the valence table of Unit 1 made operational by the parser. A bracketed atom turns this off: [C] is a bare carbon atom with zero implicit hydrogens (a reactive species, not methane), and [NH4+] must state its four hydrogens and its +1 charge explicitly. The practical lesson for later units: if you want control over hydrogens, charge or isotope, you must use brackets; otherwise the parser applies the default valence model.

2.2 Bonds

Bonds between atoms written next to each other are single by default. The symbols are - single (almost always omitted), = double, # triple, and : aromatic (also usually implicit, because lowercase atoms already imply it). So CC is ethane (a single C–C bond), C=C ethene, C#C ethyne (acetylene), and c1ccccc1 benzene with six implicit aromatic bonds. The cell draws the series so you can match each symbol to the line multiplicity in the picture.

# Bond orders: single (implicit), double =, triple #, and aromatic (lowercase ring).
bonds = [("ethane", "CC"), ("ethene (double)", "C=C"), ("ethyne (triple)", "C#C"),
         ("propene", "CC=C"), ("acetonitrile (C#N)", "CC#N"), ("benzene (aromatic)", "c1ccccc1")]
mols = [Chem.MolFromSmiles(s) for _, s in bonds]
for (name, s), m in zip(bonds, mols):
    types = sorted({str(b.GetBondType()) for b in m.GetBonds()})
    print(f"{name:22s} {s:12s} bond types present: {types}")
Draw.MolsToGridImage(mols, molsPerRow=3, subImgSize=(200, 150), legends=[n for n, _ in bonds])

2.3 Branches

A molecule is a graph, not a chain, so SMILES needs a way to step off the main path and come back: parentheses enclose a branch. CC(=O)O is acetic acid — a central carbon bearing a double-bonded oxygen (the branch (=O)) and continuing to a hydroxyl O. Branches nest, and the atom written immediately before the ( is the branch point. This is exactly the parenthesised, depth-first serialisation a computer scientist knows from writing out a tree. The cell contrasts three four-carbon skeletons that differ only in how the branches are placed — the constitutional isomers of Unit 2.

# Parentheses are branches off the preceding atom; nesting builds trees. Same formula, different topology.
branched = [("n-butane (no branch)", "CCCC"), ("isobutane (one branch)", "CC(C)C"),
            ("tert-butanol", "CC(C)(C)O"), ("acetic acid (=O branch)", "CC(=O)O"),
            ("isoprene (nested)", "CC(=C)C=C")]
mols = [Chem.MolFromSmiles(s) for _, s in branched]
for (name, s), m in zip(branched, mols):
    print(f"{name:26s} {s:14s} formula {rdMolDescriptors.CalcMolFormula(m):8s} "
          f"branch points (degree>=3 C): {sum(1 for a in m.GetAtoms() if a.GetSymbol()=='C' and a.GetDegree()>=3)}")
Draw.MolsToGridImage(mols, molsPerRow=3, subImgSize=(210, 150), legends=[n for n, _ in branched])

The branch point is always the atom written just before the opening parenthesis.

2.4 Ring-closure digits

A ring is a cycle in the graph, so a pure depth-first walk cannot express it with parentheses alone — it needs to record that two atoms, visited at different times, are bonded. SMILES does this with ring-closure digits: the same digit written after two atoms means "there is a bond between these two". C1CCCCC1 is cyclohexane — the two 1s mark the bond that closes the six-membered ring. A digit is freed once its pair is closed, so it can be reused; molecules with many rings reuse 1 and 2 repeatedly. Two-digit ring bonds use % (e.g. %10). The cell shows single rings, fused rings (naphthalene, which needs two open digits at once) and a reused digit.

# Ring-closure digits: the SAME digit after two atoms = a bond closing a ring. Digits are reused once closed.
rings = [("cyclohexane", "C1CCCCC1"), ("benzene", "c1ccccc1"),
         ("naphthalene (two rings, digits 1&2)", "c1ccc2ccccc2c1"),
         ("biphenyl (digit 1 reused)", "c1ccccc1-c1ccccc1"),
         ("indole (5+6 fused, N)", "c1ccc2[nH]ccc2c1")]
mols = [Chem.MolFromSmiles(s) for _, s in rings]
for (name, s), m in zip(rings, mols):
    print(f"{name:38s} {s:22s} rings={rdMolDescriptors.CalcNumRings(m)} aromatic_atoms={sum(a.GetIsAromatic() for a in m.GetAtoms())}")
Draw.MolsToGridImage(mols, molsPerRow=3, subImgSize=(210, 160), legends=[n for n, _ in rings])

benzene                                c1ccccc1               rings=1 aromatic_atoms=6

Figure 4. Ring-closure digits. Cyclohexane and benzene each need one digit; naphthalene is two fused six-membered rings and needs two digits open at the ring-fusion atoms (...2...2...); biphenyl shows that a digit (1) can be reused for a second, independent ring once the first has closed; indole fuses a five-membered nitrogen ring to a benzene. The printout confirms the ring counts and the number of aromatic atoms RDKit perceives. A frequent beginner bug — an unclosed ring digit — is exactly the kind of error we trigger deliberately in Section 8.

2.5 Charges, isotopes and explicit hydrogens

The decorations all live inside square brackets. Charge is written as + or -, optionally with a count: [NH4+], [O-], [Fe+2] (or the older [Fe++]). Charge matters chemically because, as Unit 1 showed, the species that actually exists at blood pH is often charged. An isotope is a leading mass number: [13C], [2H] (deuterium). Explicit hydrogens inside brackets, as in [nH] or [C@H], pin down a hydrogen the parser would otherwise infer. The cell builds a small table of charged and isotope-labelled species and draws them.

# Charges and isotopes live in [brackets]; they change formula, mass and formal charge.
deco = [("acetate anion", "CC(=O)[O-]"), ("methylammonium", "C[NH3+]"),
        ("deuterated water", "[2H]O[2H]"), ("carbon-13 methanol", "[13CH3]O"),
        ("sodium chloride (ionic)", "[Na+].[Cl-]")]
rows, mols = [], []
for name, s in deco:
    m = Chem.MolFromSmiles(s)
    rows.append((name, s, rdMolDescriptors.CalcMolFormula(m), round(rdMolDescriptors.CalcExactMolWt(m), 3),
                 Chem.GetFormalCharge(m)))
    mols.append(m)
print(pd.DataFrame(rows, columns=["species", "SMILES", "formula", "exact mass", "net charge"]).to_string(index=False))
Draw.MolsToGridImage(mols, molsPerRow=3, subImgSize=(200, 150), legends=[n for n, _ in deco])

          acetate anion  CC(=O)[O-] C2H3O2-      59.014          -1
         methylammonium     C[NH3+]   CH6N+      32.049           1
       deuterated water   [2H]O[2H]     H2O      20.023           0
     carbon-13 methanol    [13CH3]O    CH4O      33.030           0
sodium chloride (ionic) [Na+].[Cl-]    ClNa      57.959           0

Figure 5. Bracket decorations. The acetate anion and methylammonium cation carry net charges (last column), the species that actually exist at physiological pH (Unit 1). Isotope labels change the exact mass but not the formula string's element counts in the usual sense — note how [2H]O[2H] (heavy water) and [13CH3]O are reported. The last entry, [Na+].[Cl-], introduces the dot: a period separates disconnected components, so this one SMILES encodes two ions. Salts and counter-ions written with dots are the first thing a standardisation pipeline strips (Unit 4).

2.6 Stereochemistry: @ / @@ and / \

Two molecules can share the same graph yet differ in the 3-D arrangement of their atoms — the stereoisomers of Unit 2. SMILES encodes the two common kinds. Chirality at a tetrahedral centre (an atom whose four different substituents can be arranged as a left or right "hand") is written @ or @@ inside the atom's brackets: [C@H] versus [C@@H] denote the two mirror-image arrangements, read as anticlockwise/clockwise ordering of the neighbours as listed. Double-bond (cis/trans, or E/Z) geometry is written with / and \ on the bonds flanking the double bond: F/C=C/F is the trans (E) isomer, F/C=C\F the cis (Z). The cell draws both kinds; because 2-D drawings show stereo with wedges and bond geometry, the pictures differ even though the graphs are identical.

# Chirality (@/@@) and double-bond geometry (/ and \). Same graph, different 3-D -> different stereo-SMILES.
stereo = [("(R)-alanine [C@@H]", "C[C@@H](N)C(=O)O"), ("(S)-alanine [C@H]", "C[C@H](N)C(=O)O"),
          ("trans-1,2-difluoroethene (E)", "F/C=C/F"), ("cis-1,2-difluoroethene (Z)", r"F/C=C\F")]
mols = [Chem.MolFromSmiles(s) for _, s in stereo]
for (name, s), m in zip(stereo, mols):
    chiral = Chem.FindMolChiralCenters(m, useLegacyImplementation=False, includeUnassigned=True)
    bstereo = [str(b.GetStereo()) for b in m.GetBonds() if str(b.GetStereo()) != "STEREONONE"]
    print(f"{name:32s} chiral centres={chiral}  bond stereo={bstereo}")
Draw.MolsToGridImage(mols, molsPerRow=2, subImgSize=(250, 170), legends=[n for n, _ in stereo])

(R)-alanine [C@@H]               chiral centres=[(1, 'R')]  bond stereo=[]
(S)-alanine [C@H]                chiral centres=[(1, 'S')]  bond stereo=[]
trans-1,2-difluoroethene (E)     chiral centres=[]  bond stereo=['STEREOTRANS']
cis-1,2-difluoroethene (Z)       chiral centres=[]  bond stereo=['STEREOCIS']

Figure 6. Stereochemistry in SMILES. Top row: the two mirror-image forms of the amino acid alanine, differing only by @ versus @@; RDKit assigns them the R/S labels printed (the Cahn–Ingold–Prelog system of Unit 2). Bottom row: the trans (E) and cis (Z) isomers of 1,2-difluoroethene, written with / and \\; the printout shows RDKit perceiving a defined double-bond stereo. These decorations are the part of SMILES most often dropped by careless data handling — a molecule stripped of its stereo is a different, usually wrong, record.

Chemistry box — chirality, in one paragraph for a programmer

A carbon with four different groups attached can exist as two non-superimposable mirror images, like your two hands — these are enantiomers. They have identical formulae, bonds and most physical properties, but can behave completely differently in the body because biological receptors are themselves chiral (Unit 2's thalidomide story). SMILES stores the handedness as a single bit per centre (@/@@) that records the cyclic order of the neighbours. If a data pipeline throws that bit away, it has merged two genuinely different molecules — a silent, expensive error.

3. Worked example by hand: parsing a SMILES

Reading a SMILES is a short, mechanical algorithm, and doing one by hand once makes every later unit easier. We parse phenyl acetate, CC(=O)Oc1ccccc1 — it exercises every feature of Section 2 except stereo: a chain, a branch, a double bond, and an aromatic ring closed by a digit. The parser scans left to right, and each time it reads an atom it assigns the next integer atom index (0, 1, 2, …); branches and ring digits create bonds but do not consume an index of their own. for a in m.GetAtoms():
    a.SetProp("atomNote", str(a.GetIdx()))

4. Canonical SMILES: why writing order is arbitrary

The phenyl-acetate trace exposes a problem. We started the walk at a particular atom and chose a particular branch order; had we started elsewhere we would have produced a different string for the same molecule. CCO, OCC and C(C)O are all ethanol. For a database this is a catastrophe: you cannot look up a molecule by string equality if the same molecule has thousands of legal spellings.

The fix is canonicalisation: an algorithm that chooses one spelling deterministically, so that any input spelling of a molecule maps to the same canonical SMILES. The idea goes back to Morgan's 1965 algorithm for a unique machine description of a structure,[5] which assigns each atom an invariant from its graph environment (its "extended connectivity"); Weininger's CANGEN procedure[2] turned such invariants into a canonical atom ranking and hence a canonical SMILES. You do not run it by hand, but the shape is familiar: compute a canonical ordering of the nodes of a graph (like finding a canonical form under graph isomorphism), then serialise in that order. The cell demonstrates the invariance.

# Many legal spellings of one molecule all canonicalise to the SAME string.
groups = {
    "ethanol":  ["CCO", "OCC", "C(C)O"],
    "toluene":  ["Cc1ccccc1", "c1ccccc1C", "c1cc(C)ccc1", "Cc1ccccc1"],

One subtlety matters, though, and it is a classic trap: the canonical SMILES is canonical with respect to one toolkit's algorithm, not a universal standard. The caveat bears repeating because it causes real bugs.

Pitfall — "canonical" is per-toolkit, not universal

Do not compare canonical SMILES produced by different software (or different major versions of the same software) and assume equality means "same molecule", or inequality means "different". For cross-toolkit, cross-version, long-term identity you want an identifier designed by committee to be reproducible everywhere — the InChI, next — whose hashed form the InChIKey[11] is the right primary key for deduplication.

5. InChI and the InChIKey

The InChI (IUPAC International Chemical Identifier) was created to be the one identifier that every program computes identically.[3] Unlike a canonical SMILES, it is a single open-source algorithm maintained by IUPAC, so the InChI of a molecule is the same whoever computes it,[4] which is exactly what a global registry needs. An InChI is layered: a forward-slash-separated string whose layers describe, in order, the molecular formula, the atom connectivity (c), the hydrogen positions (h), then optional layers for charge (q/p), stereochemistry (t, b, m, s) and isotopes (i). The standard InChI fixes a default set of options so that everyone produces the same string. The cell decomposes the InChI of a stereo-bearing molecule into its layers.

# An InChI is layers separated by '/'. Decompose one for the amino acid alanine.
m = Chem.MolFromSmiles("C[C@@H](N)C(=O)O")           # alanine, one stereocentre
inchi = MolToInchi(m)
parts = inchi.split("/")
labels = {"c": "connectivity", "h": "H positions", "q": "charge", "p": "protons",
          "t": "tetrahedral stereo", "b": "double-bond stereo", "m": "parity", "s": "stereo type", "i": "isotope"}
print("InChI:", inchi, "\n")
print(f"  version/formula layer: {parts[0]}/{parts[1]}")
for p in parts[2:]:
    tag = p[0]
    print(f"  layer '{tag}' ({labels.get(tag, '?'):18s}): {p}")

The decomposition shows the anatomy: the string opens with the version (InChI=1S, the S marking a standard InChI), then the formula C3H7NO2, then the connectivity and hydrogen layers that any molecule has, and finally the stereo layers (t, m and s) that appear only because alanine has a defined stereocentre. A molecule with no stereochemistry simply has no t/b layers — the InChI grows only the layers it needs.

An InChI can be long, so it is impractical as a database key or a web-search term. The InChIKey solves this: it is a fixed-length 27-character hash of the InChI,[4] designed so you can paste it into a search engine or use it as a primary key. Its structure is fixed and worth knowing: 14 letters (a hash of the connectivity skeleton), a hyphen, 8 letters (a hash of the remaining layers — stereo, isotope, etc.), then a flag character and a final block (InChI version and protonation). Two molecules with the same connectivity but different stereochemistry therefore share the first block and differ in the second. The cell shows this directly.

# InChIKey anatomy: 14-char skeleton block - 8-char stereo/layer block - flag - version/protonation.
pairs = [("(R)-alanine", "C[C@@H](N)C(=O)O"), ("(S)-alanine", "C[C@H](N)C(=O)O"),
         ("alanine (no stereo)", "CC(N)C(=O)O"), ("aspirin", "CC(=O)Oc1ccccc1C(=O)O")]
rows = []
for name, s in pairs:
    k = MolToInchiKey(Chem.MolFromSmiles(s))
    b1, b2, rest = k[:14], k[15:23], k[24:]
    rows.append((name, k, b1, b2))
df = pd.DataFrame(rows, columns=["molecule", "InChIKey", "block1 (skeleton)", "block2 (stereo/layers)"])
print(df.to_string(index=False))
print("\n(R)- and (S)-alanine share block1:", rows[0][2] == rows[1][2],
      "| differ in block2:", rows[0][3] != rows[1][3])

The table shows the design working: (R)-alanine and (S)-alanine — the two enantiomers — share the first 14-character block (same connectivity skeleton) but differ in the second block (different stereochemistry), exactly as intended, while the stereo-free alanine differs again. The InChIKey is a hash, so in principle two different molecules could collide; in practice the 14-character skeleton block gives a collision probability small enough that the InChIKey is used worldwide as a de-facto compound identifier, and it is what public resources such as PubChem,[8] ChemSpider[23] and ChEMBL[9] expose for exact-structure lookup.

Chemistry box — identifier, key, hash: the same idea you already use

The InChI is a normalised representation (like a canonicalised JSON document); the InChIKey is a fixed-length hash of it (like an SHA of that document) used as a primary key. The two-block design means you can test "same skeleton, different stereo?" by comparing just the first block — a cheap near-duplicate test. This is why the next section can deduplicate a messy collection with a one-line dictionary keyed on the InChIKey.

6. Deduplicating a collection by InChIKey

A vendor catalogue, a screening library or a literature extract almost always contains the same molecule written several ways — a neutral and a drawn-charged form, two different SMILES spellings, an entry from each of two suppliers. Before any counting, modelling or purchasing you must collapse these to unique compounds, and the InChIKey is the standard tool: compute it for every record and group by it. The cell takes a deliberately messy list — aspirin written three ways, ethanol and caffeine written two ways each, and one benzene — and deduplicates it.

# Deduplicate a messy list of SMILES by standard InChIKey (group records that are the same molecule).

         "CCO", "OCC",                                                              # ethanol x2

Bridge to Unit 4 — dedup is only as good as your standardisation

Two records can be "the same drug" yet differ as a hydrochloride salt versus the free base, or as two tautomers, and then their InChIKeys differ and naive dedup keeps both. Production pipelines therefore standardise first — strip salts, neutralise, pick a canonical tautomer — and only then compute the key. The ChEMBL[10] and PubChem[11] structure-standardisation procedures are exactly this, and Unit 4 builds one.

7. File formats: MOL, SDF and PDB

A line notation is compact but carries no coordinates and only a fixed set of per-molecule data. When you need the atoms' positions, or want to attach arbitrary data fields (an assay value, an identifier, a vendor code) to each structure, you use a connection-table file format. The dominant one is the MDL MOL file[6] and its multi-molecule extension the SDF (Structure-Data File). A MOL block begins with a header (name, a line of provenance, a blank line), then a counts line stating how many atoms and bonds follow, then the atom block (one line per atom: x y z coordinates and element) and the bond block (one line per bond: the two atom indices, 1-based, and the bond order). The cell dissects a MOL block so you can see this structure literally.

When a molecule's 3-D structure matters — a conformer, or a ligand bound in a protein — the PDB (Protein Data Bank) format is the standard, because it is the format of the experimental structure archive the format is named after.[7] A PDB file lists one ATOM/HETATM record per atom with its 3-D coordinates, element and residue information, and CONECT records for explicit bonds. For small molecules it is more verbose than MOL and carries less bond detail, so you use it mainly when interfacing with protein-structure tools; those tools — docking and molecular dynamics — belong to the bioinformatics course, not this one. 8. Round-trips and where they break

A cheminformatics pipeline is a chain of conversions — SMILES in, mol object, descriptors or fingerprints out, maybe an SDF written and read again. Each conversion is a chance to lose or corrupt information, and the discipline of the field is to know which round-trips are lossless and which are not. A round-trip is lossless when parsing a string and writing it back yields the canonical form every time; the cell checks this and then shows a genuinely lossy case.

# Round-trip test: canonical SMILES should be a FIXED POINT (parse->write gives the same string back).
tests = ["CC(=O)Oc1ccccc1C(=O)O", "Cn1cnc2c1c(=O)n(C)c(=O)n2C", "c1ccccc1", "C[C@@H](N)C(=O)O"]
rows = []
for s in tests:
    canon = Chem.MolToSmiles(Chem.MolFromSmiles(s))
    twice = Chem.MolToSmiles(Chem.MolFromSmiles(canon))     # parse the canonical form and write again
    rows.append((s[:26], canon[:26], canon == twice))
print(pd.DataFrame(rows, columns=["input (trunc)", "canonical (trunc)", "fixed point?"]).to_string(index=False))
# a LOSSY round-trip: dropping stereo merges two different molecules
flat = Chem.MolToSmiles(Chem.MolFromSmiles("C[C@@H](N)C(=O)O"), isomericSmiles=False)
print("\nL-alanine written WITHOUT stereo:", flat, "-> same string as D-alanine:",
      flat == Chem.MolToSmiles(Chem.MolFromSmiles("C[C@H](N)C(=O)O"), isomericSmiles=False))

The first test confirms the good news: a canonical SMILES is a fixed point — parse it and write it again and you get the identical string, for every molecule including the stereo-bearing alanine. The second test shows the trap: writing a SMILES with isomericSmiles=False (a flag that is on by default in some older code and tutorials) drops the stereochemistry, and the two enantiomers of alanine collapse to the same string — a silent, lossy round-trip that merges two different molecules. This is the kind of bug that corrupts a dataset without raising any error, which is why Unit 4 treats standardisation as a first-class, audited step.[10]

A different failure is louder and more useful: a SMILES that is simply invalid. RDKit returns None rather than a molecule, and emits a diagnostic message. The cell deliberately feeds the parser broken strings — an unclosed branch, an unclosed ring, an impossible valence — and captures the exact error RDKit reports, so you learn to read these messages when they appear in your own work.

# Deliberately broken SMILES: RDKit returns None and reports WHY. We capture the message as a string.
import contextlib, io, re
import rdkit.rdBase as rdBase
def parse_report(smi):
    rdBase.LogToPythonStderr()                        # route RDKit's C++ log to Python stderr...
    buf = io.StringIO()
    with contextlib.redirect_stderr(buf):             # ...and capture it instead of leaking a warning
        mol = Chem.MolFromSmiles(smi)
    msg = re.sub(r"^\[\d\d:\d\d:\d\d\]\s*", "", buf.getvalue().strip().splitlines()[0]) if buf.getvalue().strip() else ""
    return mol, msg
broken = ["c1ccccc1C(", "c1ccccc", "C1CCCCC", "FC(F)(F)(F)F", "C(C)(C)(C)(C)C"]
for s in broken:
    mol, msg = parse_report(s)
    print(f"{s:18s} -> {'None' if mol is None else 'OK':4s} | {msg}")
RDLogger.DisableLog("rdApp.*")                        # re-silence logs for the rest of the notebook

c1ccccc1C(         -> None | SMILES Parse Error: syntax error while parsing: c1ccccc1C(
c1ccccc            -> None | SMILES Parse Error: unclosed ring for input: 'c1ccccc'
C1CCCCC            -> None | SMILES Parse Error: unclosed ring for input: 'C1CCCCC'
FC(F)(F)(F)F       -> None | Explicit valence for atom # 1 C, 5, is greater than permitted
C(C)(C)(C)(C)C     -> None | Explicit valence for atom # 0 C, 5, is greater than permitted

Each broken string names its own problem. c1ccccc1C( has an unclosed branch — an open parenthesis with nothing to close it — and RDKit reports a syntax error. c1ccccc and C1CCCCC open a ring-closure digit that is never matched, so RDKit reports an unclosed ring. FC(F)(F)(F)F and C(C)(C)(C)(C)C are syntactically fine but chemically impossible — five bonds on one carbon — so the valence check fails. In every case the parser returns None rather than a half-built molecule, which is the behaviour you rely on when curating data: a row whose SMILES fails to parse is dropped and logged, never silently passed downstream.

Pitfall — None is not an error you can ignore

Because MolFromSmiles returns None rather than raising, a loop that forgets to check for None will crash later with a cryptic AttributeError on a NoneType, far from the real cause. Always filter: mols = [m for m in map(Chem.MolFromSmiles, smis) if m is not None], and count how many you dropped. This is the first line of every curation script (Unit 7).

Bridge — robustness by construction: SELFIES

Because SMILES can be syntactically invalid, generative models (Unit 18) that emit SMILES character by character often produce unparseable strings. One response is SELFIES, a notation designed so that every string is a valid molecule by construction,[13] which removes a whole class of failures from molecular generation.[14] It is one of several representations — alongside fingerprints (Unit 5) and learned graph embeddings (Unit 15) — whose trade-offs are an active research topic;[20] the choice of representation is now understood to shape what a model can learn.[21][22]

10. Self-assessment

1. Write SMILES for propan-2-ol (isopropyl alcohol): a central carbon bearing two methyls and a hydroxyl. What is the branch point?CC(C)O (or equivalently CC(O)C). The central carbon, written just before the opening parenthesis, is the branch point; it bears two methyl carbons and the hydroxyl oxygen, and the parser fills its one remaining valence with an implicit hydrogen.
2. In the SMILES c1ccc2ccccc2c1 (naphthalene), what do the digits 1 and 2 mean, and why are two of them needed?Each digit marks one ring-closure bond: the two 1s bond the atoms that close the first ring, the two 2s the second. Naphthalene is two fused rings sharing an edge, so at the fusion atoms both a digit-1 and a digit-2 closure must be open at once — one digit is not enough.
3. Why do CCO, OCC and C(C)O all denote ethanol, and what single operation lets a database treat them as equal?They are three legal depth-first walks of the same three-atom graph; SMILES writing order is arbitrary. Canonicalisation — computing a deterministic atom ordering and serialising in it — maps all three to one canonical SMILES, which is what the database compares for equality.
4. A colleague compares RDKit canonical SMILES against canonical SMILES exported by another toolkit and concludes two molecules differ. What is wrong with this reasoning?Canonical SMILES is canonical only with respect to one toolkit's atom-ranking algorithm; different toolkits (or major versions) can produce different canonical strings for the same molecule. For cross-toolkit identity use the InChI/InChIKey, which is a single standardised algorithm.
5. An InChIKey is BSYNRYMUTXBXSQ-WUIGKKEISA-N for one molecule and BSYNRYMUTXBXSQ-UHFFFAOYSA-N for another. What can you infer?They share the first 14-character block, so they have the same connectivity skeleton, but differ in the second block, so they differ in a later layer — typically stereochemistry (one has defined stereo, the other not, or they are enantiomers/diastereomers). It is a cheap near-duplicate test.
6. Trace the atom indices RDKit assigns to CC(=O)O (acetic acid) and name the bond between atoms 1 and 2.Index 0 = methyl carbon; 1 = carbonyl carbon; the branch (=O) gives index 2 = the double-bonded oxygen; then index 3 = the hydroxyl oxygen. The bond between atoms 1 and 2 is a double bond (the carbonyl C=O).
7. Why is the InChIKey described as a hash, and what risk does that word imply? Why is it acceptable in practice?The InChIKey is a fixed-length (27-character) digest of the much longer InChI, so like any hash two different inputs could in principle collide. The skeleton block is long enough that collision probability is negligible across real compound collections, so it is used worldwide as a de-facto identifier and web-search key.
8. In an MDL MOL block, what does the counts line tell you, and what are the two integers at the start of each bond-block line?The counts line (line 4) states how many atoms and how many bonds the block contains. Each bond line begins with the two 1-based atom indices it connects, followed by the bond order (1 single, 2 double, 3 triple).
9. You read a vendor SDF with SDMolSupplier and find aspirin has 13 atoms, not 21. Is the file corrupt?No. SDMolSupplier removes explicit hydrogens by default during sanitisation, leaving the 13 heavy atoms. The hydrogens are implicit, not lost; pass removeHs=False if you need them explicitly (e.g. for a 3-D calculation).
10. Writing a SMILES with isomericSmiles=False made two of your records identical. What happened, and why is it dangerous?That flag drops stereochemistry, so two enantiomers (or any stereoisomers) collapse to the same string and are merged. It is dangerous because no error is raised — the dataset is silently corrupted, and a model trained on it learns that two different molecules have one set of properties.
11. Chem.MolFromSmiles("c1ccccc") returns None. What is wrong with the string, and why is returning None (rather than raising) a trap for beginners?The ring-closure digit 1 is opened but never closed — an unclosed ring. Because the function returns None instead of raising, code that does not check will fail much later with an AttributeError on a NoneType, far from the real cause; always filter out None and count the drops.
12. For each task choose SMILES, SDF or PDB: (a) a database column of 10 million structures; (b) shipping 5,000 compounds each with a measured IC50; (c) a ligand's 3-D conformer for a structure viewer.(a) SMILES — compact, one string per row, ideal as a column and for computing features. (b) SDF — stores each structure plus arbitrary data fields (the IC50) in one file. (c) PDB — the standard 3-D format understood by structure-based and protein tools.

Glossary

Branch
A side chain in a SMILES, written in parentheses off the atom that precedes the opening bracket.
Canonical SMILES
The one SMILES spelling a toolkit computes for a molecule by a deterministic atom ordering, so that any input spelling maps to it; canonical relative to that toolkit, not universal.
Canonicalisation
The algorithm that assigns a unique, graph-invariant ordering to a molecule's atoms (Morgan/CANGEN) and hence a canonical string.
Connection table
A molecule stored as explicit atom and bond tables (MOL/SDF, PDB), as opposed to a line notation.
InChI
IUPAC International Chemical Identifier: a layered, standardised string (formula, connectivity, H, charge, stereo, isotope layers) computed identically by every program.
InChIKey
A fixed-length 27-character hash of an InChI (14-char skeleton block, 8-char layer block, flag, version); used as a compound primary key and web-search term.
Isomeric SMILES
A SMILES that includes stereochemistry (@/@@, / \\); dropping it (non-isomeric) is a common lossy operation.
MOL block / SDF
The MDL connection-table format: a header, a counts line, an atom block and a bond block; an SDF concatenates MOL blocks with named data fields and $$$$ separators.
Organic subset
The elements (B, C, N, O, P, S, F, Cl, Br, I) written without brackets in SMILES, with hydrogens filled to normal valence.
PDB format
The Protein Data Bank text format for 3-D structures: one ATOM/HETATM record per atom with coordinates, plus CONECT bonds.
Ring-closure digit
A digit written after two atoms in a SMILES to mark a bond that closes a ring; freed and reusable once its pair is matched.
Round-trip
Converting a structure through a representation and back; lossless when it returns the canonical form, lossy when it drops information (e.g. stereo).
SMILES
Simplified Molecular Input Line Entry System: a depth-first string serialisation of the molecular graph.
Standard InChI
The InChI computed with IUPAC's fixed default options, so that everyone produces the same string for a molecule.
